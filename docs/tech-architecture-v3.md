# 战争纪元：2D RTS 技术方案 v3

- 日期：2026-11-10；状态：优化提案，待评审。
- 上游：[玩法优化](optimization-design-v3.md)。本文的性能数字是预算，均未实测。

## 1. 源码核查与优先级

| 级别 | 证据 | 问题及处置 |
|---|---|---|
| P0 | `Core/Simulation/Data` 三份 asmdef 的 references 均为空 | Core 使用 Simulation、Data 和默认程序集类型；Simulation 又引用 Core、VFX/UI 等。先解除依赖环，不能仅添加互相引用 |
| P0 | `SaveSystem.AutoSave` 访问 `GameManager.gameOver`，后者为 private | 静态可见的访问级别错误；以只读生命周期状态替代外部字段访问 |
| P0 | Packages、ProjectSettings 当前无文件；无场景和 Prefab | 只是源码骨架，先建立可重复打开、编译和构建的工程基线 |
| P1 | `SaveSystem` 使用 `Dictionary<string, object>` 调用 JsonUtility，加载返回 null | 改强类型快照；写成功不等于可恢复，必须往返验证 |
| P1 | `FlowFieldPathfinding` 只有一个 currentTargetCell；未发现 GenerateFlowField 调用点 | 多组目标不能共享此状态；接入目标独立的路径请求与缓存 |
| P1 | 流场默认 2400×1600、cellSize=2，每次全图 OverlapBox | 约 96 万格物理查询/次，属静态估算；地图占格替代逐格物理扫描 |
| P1 | `UnitEntity.MoveTowards` 直线移动；采矿车尝试使用全局流场，失败后也直线移动 | 统一移动系统，失败返回不可达，禁止穿越障碍兜底 |
| P1 | 单位避让遍历全体，索敌遍历敌方列表 | 空间网格限制查询范围，分摊索敌；不按摄像机位置改变战斗规则 |
| P1 | `UnitEntity.Die` 未调用 Unregister；创建初始化字段散落 | 明确单一生成/死亡入口，死亡立即退出逻辑索引，表现延迟回收 |
| P1 | `FogOfWarSystem` 雷达将整图设置为可见 | 分离逻辑视野与黑幕渲染，索敌/输入/AI 均使用逻辑视野 |
| P2 | 旧架构描述 3D LOD、mesh 实例化；决策文件选择 2D | 统一为 SpriteRenderer、Tilemap、图集与透明叠加预算 |

以上为静态检查结论，未在 Unity 编译或实机验证；源码目录均相对 `unity-project/Assets/_Project/Scripts/`。

## 2. 工程基线与迁移

继续使用 Unity 6 LTS、URP 2D Renderer、UGUI、单一输入适配层。建立工程时固定实际验证通过的 Editor 完整补丁版本，提交 ProjectVersion、Packages manifest/lock、ProjectSettings 和全部资源 meta；不同时承诺 2022 与 Unity 6 两套基线。

先把现有运行时脚本收拢到单一 `WarEra.Runtime` 程序集，移除或迁移三个嵌套 asmdef，Editor 工具使用独立 Editor 程序集。完成编译与场景冒烟后，再逐步拆成下述单向依赖，不在第一步同时重写数据与全部系统。

最终依赖（箭头表示引用）：

- `Domain`：实体 ID、命令、状态、规则及快照 DTO，仅依赖 .NET。
- `Simulation → Domain`：时间推进、经济、战斗、移动、视野及 AI；不调用 UI、音频、Transform 或单例表现服务。
- `Content → Domain`：ScriptableObject、地图导入和校验，生成不可变运行时定义。
- `Presentation → Domain`：根据只读状态和事件更新 Sprite、UI、音效。
- `App → Simulation / Content / Presentation`：显式组装服务、输入转命令、生命周期与存储适配。
- `Editor → Content / Domain`：内容创建、检查和构建工具；不进入运行时包。

现有 MonoBehaviour 保留为过渡适配器，先迁移经济、时钟与命令，再迁移实体战斗和移动。没有 profiler 证据前使用 C# 集合与集中系统更新；NativeArray、Jobs、Burst 为局部升级项，全 DOTS 不进入本轮。

## 3. 生命周期、命令与时间

状态机：Boot → Menu → Loading → Running ↔ Paused → Result → Unloading → Menu；加载或恢复失败进入 Error，并提供回菜单及错误原因。所有依赖和初始实体准备好后才能进入 Running，胜负只在 Running 的 tick 末判定。

输入 → Command → 校验 → tick 执行 → 状态与事件 → 只读表现。Command 包含 tick、玩家 ID、递增序号、实体 ID 列表和参数。按 tick/玩家/序号排序；拒绝重复序号、过期实体、越界目标和非法资源消耗。错误码供 UI 显示，不让 UI 自行推算扣款结果。

模拟固定 20Hz，渲染独立 30/60FPS 并插值；每帧最多追赶 4 tick，超限保留积压并记录降速，不丢弃已收取的命令。切后台冻结 tick，恢复后不把后台时长用于追赶。暂停时不执行游戏命令，允许菜单及存档操作。

每 tick 顺序固定：执行命令与资源预留 → 推进施工/生产与采集 → 更新移动和空间索引 → 更新视野 → AI 决策（命令最早下 tick 执行）→ 生成攻击与到期伤害事件 → 批量伤害/死亡 → 清理索引与检查胜负 → 发布只读结果。

冷却统一保存为 tick，不使用协程/真实时间触发逻辑伤害。随机源携带种子和完整状态。稳定顺序支持同版本问题复现，但浮点、跨版本与跨平台差异仍可能影响结果；当前不承诺确定性锁步或“直接接网络即可多人”。

## 4. 数据、空间与移动

逻辑地图为 XY 平面，位置使用逻辑格连续坐标，Z 只用于表现；等距投影和逆投影由同一转换器负责。地图给出 origin、cellSize、width、height；超边界请求必须先拒绝，不能先 Clamp 再判断合法。

实体采用稳定 ID 与代数（generation），状态与视图引用分离；池化重用不得复用旧命令中的有效身份。定义数据包括显式 armorType、weaponType、footprint、movementClass、成本、时长和前置条件；升级修改运行时派生值，不修改共享 SO。

地图源数据为 JSON，编辑器导入与校验后生成运行时数据；单位与建筑以 SO 为本轮唯一编辑源，不同时维护一套手抄 JSON 数值。主题清单用 `themeId + definitionId` 稳定标识，并记录 schemaVersion、contentVersion 与内容指纹。

空间查询使用均匀网格，格尺寸按交战密度调优。避让、范围伤害和索敌只查询邻格候选。死亡立即标记并从可查询集合排除；批次结束统一回收，避免遍历中修改集合。

寻路先保证正确性：切片采用可缓存的 A*，每帧按节点扩展预算调度请求，寻路未完成时单位等待或沿仍有效路径前进。对角边检查两侧占格；单位尺寸通过 movementClass 的通行网格体现；终点被占用时寻找可达停靠格，无法找到返回原因。

体验验证版若群体请求实测昂贵，再增加流场：使用优先队列 Dijkstra 计算带权代价，禁止把普通 FIFO 加固定遍历次数视为正确带权最短路。缓存键为目标格、移动类型、地图通行版本，活跃流场最多 8 个，LRU 淘汰；不同目标不得覆盖同一个全局方向场。预算耗尽保留旧有效路径或等待，不允许直线穿墙。

静态障碍由地图生成，建筑施工确认时写入占格并增加版本；路径与流场在版本失效后重新请求。建设会堵死关键通路时拒绝确认。采矿车和战斗单位共享移动系统，避免各自保留不一致的寻路兜底。

## 5. 2D 表现与视野

地形采用分块 Tilemap，单位与建筑用 SpriteRenderer；图集按主题与用途拆分，依材质、透明排序及实际批次检查结果调优，不承诺一张图集必然一次绘制。等距排序使用统一脚点，建筑多部件通过 SortingGroup 组合；阴影使用可关闭的贴地精灵。

首轮静态图加后坐、履带/脚步提示保证可读性，正式动画按“待机/移动/开火/死亡”补齐。红警类视觉参考转化为辨识度、比例和对比要求，不把现有 AI 单张素材标为完整八方向动画。

视野权威数据按玩家独立保存 explored 与 visible；逻辑更新不可依赖画面分辨率和黑幕纹理采样。表现把逻辑结果上采样到遮罩，低档降低遮罩和特效质量，不降低交战判定频率。采矿、战斗、生产不按是否位于镜头内变速。

子弹、爆炸、音源和血条视图池化；数量达上限时优先保留关键命中反馈并裁剪远处装饰。短音效和音乐分别设置导入策略，使用 AudioClip 导入后的实际内存测量，不用文件扩展名判断运行内存。

## 6. 存档与恢复

使用可序列化字段构成的强类型 DTO，避免 `Dictionary<string, object>` 作为 JsonUtility 输入；具体支持范围按固定 Editor 版本验证。设置可保留 PlayerPrefs；战斗快照写入 persistentDataPath 下独立文件。

快照至少包括：schema/contentVersion、地图与主题指纹、当前 tick、随机状态、双方经济与升级、全部实体 ID/代数/HP/位置/订单、生产与施工队列及预付金额、采矿状态与携带量、矿点余量、攻击冷却、未结算范围伤害、AI 状态、探索格、待执行命令及序号。当前可见格和空间索引从快照重建。

在 tick 边界取得一致快照，在后台序列化与写入。先写临时文件并校验，再按平台验证过的文件替换策略切换为正式档，保留上一份备份；校验用于发现截断损坏，不代表防篡改。自动档独立于手动档，不覆盖手动槽。

恢复先验证版本和内容，再在独立上下文建立实体、重连 ID 引用、重建索引并校验不变量，成功后才替换当前会话。坏档尝试备份；未知版本/缺失主题给明确错误并保留原档。切后台尽力保存，30 秒周期快照作为补充，不能承诺进程被强杀时回调一定完成。

## 7. 性能预算与测量

以下统一压力场景：80 移动实体、40 建筑、60 个视觉投射物、持续生产与采集、范围爆炸、双向命令及迷雾更新。所有画质档使用相同逻辑数量上限。

| 项目 | 初始目标 | 测量方法 |
|---|---|---|
| 低档帧时间 | P95 ≤33.3ms，P99 ≤50ms | 热机后连续 10 分钟；记录实际呈现间隔 |
| 中档帧时间 | P95 ≤16.7ms，P99 ≤33.3ms | 同一存档、命令序列、分辨率档位 |
| 模拟单 tick | P95 ≤5ms，P99 ≤8ms | 分开记录移动、视野、战斗、经济 |
| 寻路调度 | 主线程每帧预算 2ms | 记录排队延迟；20 个请求 P95 ≤500ms |
| 稳态 GC | 逻辑热循环 0 B/tick | 预热后排除菜单、存档和加载过程 |
| 总进程内存 | 低档峰值目标 ≤700MB | 报告纹理/托管/原生与进程值，避免混为一个指标 |
| 重入战场 | 10 次后稳定内存相对首次预热增量 ≤10% | 同条件快照，排查对象数量及资源句柄 |

第一次实机验证必须记录具体机型、系统、Editor/包版本、构建参数与温度条件，再决定支持设备范围。预算达不到时依次检查数据规模、查询热点、纹理尺寸与透明叠加，最后再对热点引入 Jobs；禁止通过减少低档玩家可用兵力达标。

## 8. 内容包与扩展边界

切片仅本地二战资源，加载经 IContentProvider 接口；不先部署 CDN 和远程目录。第二时代通过同一接口加载本地包，验证不修改核心经济/战斗分支即可配置差异；主题能力允许近战、冲锋等扩展，不承诺五时代只是换名称。

需要远程包时再引入 Addressables：显式记录句柄所有者，退出战场释放视图与句柄；以资源计数和内存快照验证释放，不依赖强制 GC 作为资源管理方案。商业化授权与加载分离，取消下载/失败不改变当前已加载会话。

## 9. 官方依据与适用边界

- [Unity 程序集介绍](https://docs.unity.com/en-us/engine/6000.0/manual/programming-environment/script-compilation/assembly-definition-files/assembly-definitions-intro)：自定义程序集有独立依赖边界，不能把默认程序集当作反向依赖解决环。
- [Unity JsonUtility](https://docs.unity.com/en-us/engine/6000.3/script-reference/unityengine/jsonutility)：使用明确的可序列化状态类型；本项目仍需在所固定版本做往返测试。
- [Unity 2D Tilemap 性能指南](https://unity.com/how-to/optimize-performance-2d-games-unity-tilemap)：支持把 Tilemap 和图集作为 2D 地图优化方向；本文预算来自项目目标，并非该指南的性能保证。
