## 1. 引擎选型结论

**推荐：Unity 6 LTS（URP）**

| 维度 | Unity 6 + URP | Godot 4.x | Unreal 5 |
|---|---|---|---|
| 移动端 RTS 适配 | ★★★★☆ ECS/DOTS 可做大量单位 | ★★★☆☆ 3D 移动端生态较薄 | ★★☆☆☆ 包体与发热不适合手机 |
| 大量单位处理 | ★★★★★ DOTS / Job System | ★★★☆☆ 多线程刚成熟 | ★★★★☆ Mass 系统强但重 |
| 移动端 UI 系统 | ★★★★★ UGUI / UI Toolkit 成熟 | ★★★☆☆ Control 节点够用 | ★★☆☆☆ UMG 在手机上偏重 |
| 美术资产管线 | ★★★★★ 工具链最全 | ★★★☆☆ 依赖社区 | ★★★★★ |
| 包体（IL2CPP Strip） | 基础约 35–50MB | **基础约 25–35MB（最优）** | 基础 200MB+（淘汰） |
| 成熟商业案例（移动 RTS） | 大量 | 极少 | 少数 |
| 学习/招人成本 | 低 | 中 | 高 |

**最终结论**：Unity 6 LTS + URP。理由——
1. 移动端 RTS 的核心痛点是**大量单位 + 触屏 UI**，Unity 这两块同时是行业最成熟；
2. DOTS/Job System 能撑住 100 单位 + 100 发子弹的实时模拟；
3. 包体比 UE 小一个数量级，且可做到和 Godot 接近（见 §8 包体控制）。

> 若项目目标偏"轻量单机、包体极小、2 人小团队"，Godot 是可接受的降级选项，但需自建大量工具链。

## 2. 性能预算（三档设备）

| 指标 | 低端（骁龙 6xx / A12 及以下） | 中端（骁龙 7xx / A14–A15） | 高端（骁龙 8xx / A16+） |
|---|---|---|---|
| 目标帧率 | 30 FPS 锁 | 60 FPS | 60 FPS |
| 同屏单位上限 | **40** | **80** | **120** |
| 同屏投射物 | 60 | 120 | 200 |
| Draw Call | ≤ 120 | ≤ 200 | ≤ 300 |
| 三角面 / 帧 | ≤ 80K | ≤ 200K | ≤ 400K |
| 纹理内存 | ≤ 180MB | ≤ 350MB | ≤ 600MB |
| 总内存占用 | ≤ 1.0GB | ≤ 1.6GB | ≤ 2.2GB |
| 单局 CPU 主线程 | ≤ 22ms | ≤ 12ms | ≤ 12ms |
| 电池/发热 | 必须锁 30fps + 降分辨率 | 正常 | 正常 |

**关键决策**：低端机**主动锁 30 FPS**，不要试图硬跑 60——RTS 的体验瓶颈在操作与决策，不在帧率；但发热掉帧会让玩家断线式体验崩塌。

## 3. 渲染优化方案

### 3.1 LOD 策略

| 对象 | LOD0（近） | LOD1（中） | LOD2（远） | 剔除 |
|---|---|---|---|---|
| 步兵 | 2500 面 + 骨骼 | 800 面 + 简化骨骼 | 200 面，无骨骼，动画合批 | 屏幕外 |
| 载具 | 4000 面 | 1500 面 | 300 面 + 烘焙姿态 | 屏幕外 |
| 建筑 | 5000 面 | 2000 面 | 500 面 | 视距外 |
| 地形装饰 | 300 面 | 80 面 | 剔除 | 视距外 |

**切换距离按缩放级别动态调整**（RTS 会拉远拉近，不能固定距离）：`switchDist = baseDist × (1 / cameraZoom)`。

### 3.2 Draw Call 合并策略

| 场景 | 方案 | 说明 |
|---|---|---|
| 同类型单位（如 20 个动员兵） | **GPU Instancing** | 共用 mesh + 材质，各自 instance 矩阵与动画时刻 |
| 静态建筑 | **Static Batching** | 场景预合批，运行时零开销 |
| 地形 | **单一 Terrain Mesh + Splat Map** | 不做 tile 分块，一张大 mesh 一次绘制 |
| UI | **Sprite Atlas 合图** | 全部 UI 一张图集，UI 只需 2–4 个 Draw Call |
| 特效粒子 | **Particle System 合批 + 图集** | 同材质粒子合并为一个 draw |
| 单位血条 | **UI 层统一渲染（Screen Space）** | 不要用 3D sprite 血条，会爆 DC |

**目标**：战场本体（地形 + 单位 + 建筑）≤ 60 Draw Call；UI ≤ 10；特效 ≤ 40。

### 3.3 地形方案

| 方案 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| Tile-based（网格拼块） | 美术直观、合批容易 | 大地图 tile 数量爆炸 | ❌ 不选 |
| **Mesh-based（单张地形 mesh + Splat）** | 一次绘制、可做 LC 地形 | 需要美术做整体地形 | ✅ **选这个** |
| 高度图 + 顶点色 | 最省 | 细节表现弱 | 可作低端机降级方案 |

地图尺寸建议 **512×512 米**，网格 2m 一格做寻路。

### 3.4 雾效与可视裁剪

- 用**视野遮罩（黑幕）** 而非体积雾——RTS 的战争迷雾是"信息遮蔽"，不是粒子特效。
- 迷雾实现：一张 `128×128` 的 `RenderTexture` 做模糊，只更新玩家单位附近的格子（脏区域刷新）。
- 视锥剔除 + 手动距离剔除（超过摄像机视野 1.5 倍距离的对象直接不渲染）。
- **不要用 Unity 内置的 Occlusion Culling**——RTS 俯视视角下几乎无效，只浪费烘焙时间。

## 4. 大量单位管理

### 4.1 单位更新 LOD（最重要的一条）

| 单位位置 | AI 更新频率 | 动画 | 状态同步 |
|---|---|---|---|
| 屏幕内 + 近 | 30/60 Hz | 完整 | 实时 |
| 屏幕内 + 远 | 15 Hz | 简化（Idle/Move 两态） | 实时 |
| 屏幕外 + 玩家领地 | 5 Hz | 不渲染 | 5 Hz |
| 屏幕外 + 交战中 | 10 Hz | 不渲染 | 10 Hz |

> **A/B 分队**：把所有单位分成两批，A 批本帧更新、B 批下帧更新，等效把 AI 计算减半，玩家感知不到。这是 RTS 里性价比最高的一条优化。

### 4.2 寻路方案

| 方案 | 适用 | 代价 | 结论 |
|---|---|---|---|
| Unity NavMesh | 少量单位 | 大量 Agent 时主线程爆炸 | ❌ 不主用 |
| **Flow Field（流场）** | **大部队同目标移动** | 需要预计算区域 | ✅ **主方案** |
| A* + 路径缓存 | 少量单体 | 每次寻路有尖峰 | ✅ 辅助 |
| 分组寻路（Group Pathfinding） | 编队移动 | 只算 1 条路，成员跟随 | ✅ 配合流场 |

**推荐组合**：
1. 玩家下达"移动到 X"→ 为目标点生成 **Flow Field**（周围 64×64 区域，预计算一次）；
2. 单位按流场方向走，不需要各自寻路；
3. 遇障碍（建筑挡住）时局部重算受影响格；
4. 流场计算放到 **Job System 多线程**，每帧最多更新 2 个流场。

**性能差**：100 单位 A* 寻路单帧约 15–25ms（卡死）；Flow Field 一次计算约 2–4ms，可摊帧。

### 4.3 战斗结算策略

| 优化 | 做法 |
|---|---|
| 空间分区 | 用 **均匀网格（Uniform Grid）** 而非 QuadTree——RTS 单位分布均匀，网格更快 |
| 目标查询 | 每 0.2s 查一次附近敌人（不是每帧），结果缓存 |
| 伤害结算 | 攒到帧末批量处理，避免一次爆炸触发上百次独立回调 |
| 子弹 | 视觉子弹用对象池，逻辑伤害**即时命中**（hitscan），不需要子弹飞行模拟 |
| 群体伤害 | 一次 AOE 用一次空间查询拿全部目标，而不是每个目标查一次 |

### 4.4 ECS vs MonoBehaviour

| 方案 | 大量单位表现 | 开发速度 | 结论 |
|---|---|---|---|
| 纯 MonoBehaviour | 80 单位开始吃力 | 快 | ❌ 不选 |
| **混合：单位数据用 struct 数组 + 系统更新，渲染用 GameObject 池** | **120 单位流畅** | 中 | ✅ **推荐** |
| 全 DOTS/ECS | 1000 单位无压力 | 慢，学习曲线陡 | 过度设计 |

**推荐"混血方案"**：单位的**逻辑数据**（位置/HP/目标/状态）放在 `NativeArray` 里，用 Job System 批量更新；**渲染**还是 GameObject + GPU Instancing。开发体验和性能的平衡点。

## 5. 内存管理

### 5.1 资源加载

| 资源 | 加载时机 | 方式 |
|---|---|---|
| 核心 UI / 通用音效 | 启动时常驻 | Resources 或 Addressables 预载 |
| 关卡地形 / 建筑 | 进入关卡时 | **Addressables 异步加载 + 加载进度条** |
| 单位模型 | 按需，按阵营分包 | Addressables Label 分组 |
| 特效贴图 | 首次使用时加载 | 预载常用特效，冷门懒加载 |

**原则**：单局所需资源 ≤ 400MB。切换关卡必须 `Resources.UnloadUnusedAssets()` + 显式释放。

### 5.2 纹理压缩

| 平台 | 格式 | 说明 |
|---|---|---|
| Android | **ASTC 6×6**（主力）/ ASTC 8×8（低端降级） | 不是 ETC2——ASTC 质量高得多，且现代 Android 全支持 |
| iOS | **ASTC 6×6** | A 系列芯片原生支持 |
| 特殊（法线/UI） | ASTC 4×4 | 高质量需求 |
| 兜底 | ETC2 | 仅用于极老设备（可放弃） |

**尺寸预算**：单位贴图 512×512（共享图集）；建筑 1024×1024；地形 Splat 2048×2048；UI 2048×2048 一张图集。

### 5.3 对象池

| 池 | 容量 | 说明 |
|---|---|---|
| 子弹（视觉） | 200 | 超出则复用最老的一个 |
| 特效实例 | 150 | 按类型分池，避免复用错类型 |
| 单位 | 按阵营 120 | 死亡不销毁，隐藏回池 |
| 伤害飘字 | 80 | UI 层 |
| 音效 AudioSource | 32 | 见音频方案 |

**铁律**：**战斗中零 `Instantiate` / 零 `Destroy`**。开局预实例化所有池，战斗中只做 `SetActive` 与位置更新。

## 6. 触屏交互技术方案

### 6.1 输入系统

用 Unity **Input System（新版）**，不用旧 Input Manager。

| 手势 | 技术实现 |
|---|---|
| 单指拖动 = 镜头平移 | 单指 `Press` 后位移 > 10px 判定为拖动，取消点击判定 |
| 单指点击 = 选中 | `Release` 时位移 < 10px 且时长 < 250ms 判定为点击 |
| 长按 = 框选 / 弹出菜单 | `Press` 持续 300ms 进入长按态 |
| 双指捏合 = 缩放 | 两指距离变化率映射到正交摄像机 `orthographicSize` |
| 双指点击 = 快速回基地 | 双指同时 `Press` 且时长 < 200ms |

**点击判定**：不要用 3D 射线点模型——用**逻辑层判定**：把屏幕坐标反投影到地面平面，在 32pt 半径内找最近的单位。这比物理射线快 10 倍且更适合手指。

### 6.2 摄像机控制

- **正交摄像机（Orthographic）**，不用透视——RTS 必需，且更省性能。
- `orthographicSize` 范围：`8`（近）到 `24`（远）。
- 边界限制：摄像机中心限制在地图范围内（留 5m 边）。
- **不实现"边缘推屏"**——触屏上没有鼠标边缘，别抄 PC 的设计。
- 拖到屏幕边缘时加速平移（边缘加速带 100px）。

### 6.3 UI 性能

- UI 用 **UGUI + 图集**，不用 UI Toolkit（移动端 UGUI 性能更可控）。
- 关闭 `Raycast Target`（除可交互元素），否则每次点击都遍历整棵 UI 树。
- **血条不用 UI 元素**：用一次性的 `Graphics.DrawMeshInstanced` 画全军血条，1 个 Draw Call 搞定 120 个单位血条。

## 7. 项目架构

### 7.1 目录结构

```
Assets/
├── _Project/                      # 项目自有资源（最上层，优先编译）
│   ├── Scripts/
│   │   ├── Core/                  # 框架：事件总线、时间管理、服务定位
│   │   ├── Simulation/            # 单位逻辑（NativeArray + Job）
│   │   │   ├── Units/             # 单位数据与状态机
│   │   │   ├── Combat/            # 伤害结算、目标查询
│   │   │   ├── Pathfinding/       # Flow Field、Grid
│   │   │   └── Economy/           # 资源、生产队列
│   │   ├── Presentation/          # 表现层：渲染、动画、特效、音频
│   │   ├── Input/                 # 输入与手势
│   │   ├── UI/                    # 界面
│   │   └── Data/                  # ScriptableObject 配置
│   ├── Art/                       # 模型、贴图、材质
│   ├── Audio/                     # 音频
│   ├── Prefabs/                   # 预制体
│   └── Scenes/                    # 场景
├── ThirdParty/                    # 第三方（不进版本控制细节）
└── Settings/                      # URP 与项目设置

docs/                              # 设计/技术文档（不进包体）
tools/                             # 构建脚本、数据导出（不进包体）
tests/                             # 测试（不进包体）
export/                            # 导出产物（gitignore）
```

**核心分层原则**：`Simulation` 层**不引用**任何 `UnityEngine.Rendering` / UI / Audio API；`Presentation` 层只读 Simulation 数据。这样逻辑可测试、可回放、可未来做多人。

### 7.2 核心模块划分

| 模块 | 职责 | 关键接口 |
|---|---|---|
| `GameClock` | 统一时间源，支持暂停/倍速 | `Tick(float dt)` |
| `UnitRegistry` | 所有单位的 NativeArray 存储 | `NativeArray<UnitData>` |
| `UnitSystem` | 每帧更新单位状态机 | `Update()` (Job) |
| `SpatialGrid` | 空间查询 | `QueryRadius(pos, r)` |
| `PathfindingSystem` | 流场生成与查询 | `GetDirection(pos)` |
| `CombatSystem` | 伤害结算 | `ResolveDamage()` |
| `EconomySystem` | 资源与生产队列 | `Produce(unitId)` |
| `AIController` | 敌方 AI 行为树 | `Tick()` |
| `ViewSync` | Simulation → 渲染同步 | 每帧同步 transform |
| `InputRouter` | 手势 → 命令 | `OnCommand` 事件 |

### 7.3 网络扩展预留

当前是**单机**，但为了未来加多人，做三件事（成本极低）：

1. **命令模式化**：所有玩家操作转成 `Command` 结构体（`MoveCommand{ unitIds, targetPos }`），而不是直接改单位状态。
2. **确定性**：所有逻辑用**定点数或有明确浮点约束**，随机用带种子的伪随机。
3. **逻辑与表现彻底分离**（§7.1 已做）。

这样未来做 lockstep 多人时，只需同步 `Command` 流，不需要重写逻辑。

## 8. 多平台打包

### 8.1 包体控制

| 措施 | 收益 |
|---|---|
| IL2CPP + Managed Stripping Level: High | −15MB |
| 剔除未使用的引擎模块（Strip Engine Code） | −20MB |
| 纹理 ASTC 压缩 | −40% 纹理体积 |
| 音频 AAC/OGG 压缩（不用 WAV） | −60% 音频体积 |
| 首次启动按需下载关卡资源（Addressables Remote） | 首包可控制到 150MB 内 |

**目标**：首包 ≤ 200MB（免应用商店 Wi-Fi 限制的痛），完整包 ≤ 800MB。

### 8.2 平台差异

| 项 | iOS | Android |
|---|---|---|
| 图形 API | **Metal** | **Vulkan**（低端降级 GLES3） |
| 最低支持 | iOS 14+ | Android 8.0（API 26）+ Vulkan |
| 音频延迟 | 低 | 需要 `AudioConfiguration` 调 `best latency` |
| 后台行为 | 必须能暂停恢复不丢状态 | 同 |
| 热更新 | **禁止代码热更**（合规风险） | 可做资源热更（需合规评估） |

### 8.3 发布前必过检查

- [ ] 低端机（如 iPhone XR / Redmi Note 系列）跑通 30fps
- [ ] 冷启动到进入战斗 ≤ 8 秒
- [ ] 战斗中断（来电/切后台）恢复后状态正确
- [ ] 内存峰值不触发系统杀进程
- [ ] 各分辨率（16:9 / 19.5:9 / 平板 4:3）UI 无遮挡
- [ ] 竖屏切换不崩溃

## 9. 技术风险清单

| 风险 | 概率 | 影响 | 缓解 |
|---|---|---|---|
| 大量单位 AI 主线程卡顿 | 高 | 高 | Flow Field + 更新 LOD + A/B 分队（§4.1/4.2） |
| 低端机发热降频 | 高 | 中 | 主动锁 30fps + 动态分辨率缩放 |
| 触屏框选体验差 | 中 | 高 | 做原型先测手势，别等到后期 |
| 包体超 200MB | 中 | 中 | Addressables 分发关卡资源 |
| 项目后期才发现架构撑不住 | 中 | 极高 | **Demo 阶段就必须在低端机测 80 单位** |
